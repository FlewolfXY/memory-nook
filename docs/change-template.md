# 每轮变更记录模板

复制到 CHANGELOG.md 顶部，分配递增 LOG 编号。真实结果不知道时写“未验证”或“失败及原因”；不留一句“完成优化”替代证据。

## LOG-NNN · 日期 UTC · 用户可理解的标题

- **目标与触发**：用户要完成哪个动作；来自哪条明确要求/反馈；与产品基准的关系。
- **基准版本**：开始时的源码 SHA、公开镜像 SHA、应用发布版本；存在已有修改时说明保留范围。
- **本轮完成**：具体行为、模型、文案、来源或基础设施变化；重要文件/函数。
- **用户可见结果**：用户现在能看到或完成什么；文档轮说明无应用变化。
- **数据影响**：原文、图片、物件身份、位置、来源关系是否变化；迁移、旧数据保护、失败恢复和不可逆影响。无则写无。
- **验证证据**：命令/用例与结果；需要时附可重现 fixture、运行记录、截图或实际交互录像。测试与浏览器结果分别写。
- **用户反馈**：原话或忠实转述、对应版本、已接受/待确认/已否定；不能代用户验收。
- **未完成与风险**：具体未验证项和失败项，连接到 PROGRESS 中稳定的 F/R 编号。
- **发布与携带**：本轮是否同步 GitHub、是否部署；提交、workflow/发布证据。未完成同步如实说明原因。
- **回退**：怎样撤销代码；怎样处理数据。代码回退不自动等于数据库回退。若是回滚，另写一条新日志，不删除被撤销条目。
- **下一步**：一个明确片段与完成条件，引用 ROADMAP。

## 同步总进度

更新 PROGRESS：版本基准、受影响工作流、开放发现、验证债务、当前与下一片段。已完成代码但未浏览器验证，分别标注。CURRENT_SLICE 只保留这轮目标、范围、结果和下一步，不累加多个“当前”。

若改变产品定义、来源规则或审美基准，另更新 PROJECT_BRIEF/DECISIONS；正常小修改无需重写全部文档。文件路径相对仓库，日志引用的证据必须实际存在。

## 提交与同步的具体办法

实现和对应记录放在同一提交；提交标题含 LOG 编号。记录确切“开始基准”；本提交的 SHA 可由 Git 历史确定，不将它硬写回自身制造循环提交。后续发布回执若需要落文件，可以单独提交，标为日志/发布元数据更新，引用同一 LOG 编号，并同步 PROGRESS；无行为变化无需另发应用版本。

提交前查看 git diff：有改动却没有本轮日志/总进度更新，则先补齐。这个检查是代理责任，不把补日志变成向用户索要批准的流程。没有进行改变的问答不必为凑记录造提交。
